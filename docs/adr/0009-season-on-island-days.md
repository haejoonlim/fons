# ADR 0009 — 계절은 섬일로 센다

## 맥락

GDD 04 §3.13 한 절 안에 시간축이 둘이다.

- "낮밤·사계절은 섬 시간 기준 (계절 1바퀴 = 섬 90일 = **현실 약 13일**)"
- "계절 (월 기준 · 가안): 봄(3~5월) … 겨울(12~2월)"

그리고 같은 절의 2026-09-29 정정 블록은 원본 코드 `EstateSystem.CurrentSeason` 이 `nowUtc.Month` 로 계절을 고른다고 적었다. 데이터도 같은 쪽이다 — `data/estate.json` 의 `farming.seasons[].months` 가 `[3,4,5]`·`[12,1,2]` 다. 즉 문면·데이터·원본 코드가 서로 다른 시간축을 가리키고 있다.

세이브 설계가 `estate` 시계를 섬일로 잡으면서([ADR 0008](0008-save-schema.md) · [설계](../design/세이브_불러오기_설계.md) §4) 이 모순이 실제 코드에 닿게 됐다. 계절을 저장하지 않으려면 계절이 무엇의 함수인지 먼저 정해야 한다.

## 대안

1. **기기 월** — 현행 데이터·원본 코드. 3~5월이 봄. 계절 판정에 ×7 배속이 걸리지 않는다.
2. **섬일** — §3.13 첫 문장. 섬 90일이 한 계절, 365섬일이 한 해.
3. **계절 없음** — 계절 보정을 데이터에서 지우고 상시 평시로 둔다.

## 결정

**2번.** 1계절 = 섬 90일, 1년 = 365섬일. 4×90 = 360 이므로 남는 5일은 겨울에 붙인다(271~365일). `data/estate.json` 의 `seasons[].months` 를 `seasons[].island_days = [시작, 끝]` 로 바꾸고, 달력 월 표기는 폐기한다. 원본 코드의 `nowUtc.Month` 판정은 **이관하지 않는다.**

이유는 경제 축이 이미 하나이기 때문이다. 세금·식량 소비·자연증가·채집 쿨·농사 성장·유지비가 전부 섬 하루 기준이고(04 §3.13, 2026-09-17 확정), 04 §3.2 는 "런 기간(섬일)이 영지 경제의 유일한 시간 변수"라고 못박았다. 계절만 기기 월에 두면 시간 변수가 둘이 된다.

기기 월 기준의 실제 비용도 크다. 기준 페이스는 100층 ≈ 50섬일 ≈ 현실 7일이다(04 §3.2). 계절이 달력 월이면 한 런이 거의 한 계절에 갇히고, 12월에 시작한 런만 겨울 식량 −30% 를 런 내내 맞는다. 계절이 밸런스 변수에서 **시작 날짜 운**으로 바뀐다 — 04 §3.13 이 계절을 영지 경제 보정으로 둔 의도와 다르다.

## 결과

**얻은 것**

- 영지의 시간축이 하나다. 세이브는 `clock_epoch`·`last_settled_day` 만 들고, 계절은 섬일에서 파생한다 (저장하지 않는다).
- 50섬일 런이 계절 경계를 최대 한 번 지난다. G-15 의 "겨울 포함 구간 관찰" 검증이 실제로 성립한다.
- 계절 판정이 기기 시계 조작에 흔들리지 않는다.

**잃은 것**

- 현실 계절과 무관해진다. 3월에 시작해도 섬의 봄이 아니다 — 표시 문구에서 달력 월을 쓰지 않는다.
- 365 를 4로 나눈 나머지 5일을 겨울에 붙인 것은 임의 결정이다. 계절 보정이 5일 더 길어지는 만큼 겨울 식량 압박이 아주 조금 길다.
- 원본 저장소가 GDD 를 개정하기 전까지 `docs/gdd/GDD_v8.0_04_영지.md` 문면은 두 기준을 계속 들고 있다. 이 저장소는 GDD 를 고치지 않으므로([AGENTS.md](../../AGENTS.md) §3), 그동안 이 ADR 이 우선한다.
- G-15 의 겨울·흉작 강도 재측정은 아직이다. 계절 길이가 섬일 고정이 되어 시뮬의 "전 기간 겨울 근사"와 실제 분포가 갈릴 수 있다 — 시뮬 시나리오에 계절 순환이 들어갈 때 다시 본다.
