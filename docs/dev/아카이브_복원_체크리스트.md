# 아카이브 복원 체크리스트

원본 Unity 클론을 새 폴더에 다시 세우는 절차. 위에서부터 그대로 실행하고, `기대`와 다르면 그 자리에서 멈춘다. 배경과 선택 근거는 [원본클론_정리_선택지.md](원본클론_정리_선택지.md) §5.

## 0. 준비

이 절차 전체를 한 명령으로 돌릴 수 있다. 항목이 어긋나면 어느 것인지 찍고 exit 1 로 끝난다.

```bash
./.venv/bin/python tools/verify_archive.py                 # 38개 항목 · 17~22초
./.venv/bin/python tools/verify_archive.py --skip-regen    # 재생성(8초)을 건너뛴다 · 36개 · 약 15초
```

아래는 같은 검사를 손으로 따라가는 순서다 — 새 환경이거나 도구를 못 믿을 때 쓴다. 도구는 아카이브를 읽기만 하고, 작업 폴더는 시스템 temp 에 만들어 끝나면 지운다(`--keep` 이면 남긴다).

```bash
A=~/Desktop/soul-commander-archive-2026-10-24
OUT=/tmp/fons-restore
mkdir -p "$OUT"
ls "$A"/sha256.txt "$A"/soul-commander-2026-10-24.tar.gz "$A"/uncommitted-restore.patch \
   "$A"/untracked-2026-10-25.bundle
```

기대: 네 파일이 다 있다. `uncommitted.patch` 는 기록물이라 복원에 쓰지 않는다 — 이진 hunk 가 잘려 `git apply` 가 거부한다. bundle 은 미추적 37개만 담는다 — tar 가 없어도 이 파일만으로 꺼낸다(10단계).

## 1. tar 자체 확인

```bash
cd "$A" && shasum -a 256 -c sha256.txt && gzip -t soul-commander-2026-10-24.tar.gz && echo GZIP_OK
```

기대: `soul-commander-2026-10-24.tar.gz: OK` · `untracked-2026-10-25.bundle: OK` · `GZIP_OK` (자체 실측 · 2026-10-25). tar 가 실패하면 아래는 의미가 없다.

## 2. 풀기

```bash
tar -xzf "$A"/soul-commander-2026-10-24.tar.gz -C "$OUT"
find "$OUT" -type f | wc -l
```

기대: **1,652** (프로젝트 1,616 + `.git` 36). 이 수는 `.git` 을 포함하므로 git 명령을 한 번이라도 돌린 뒤에는 달라진다 — 아래 단계는 `.git` 을 뺀다.

## 3. 이력이 성한지

```bash
cd "$OUT"
git rev-parse HEAD
git rev-list --count HEAD
git fsck --full; echo "fsck exit=$?"
```

기대:
- `669f0be936cec1e4ac3fc84f3af6a0fa7f60fe9f`
- `252`
- `fsck exit=0` 에 출력 0줄

## 4. 풀린 트리 상태 (A 경로는 여기서 끝)

```bash
git -c core.quotepath=false status --porcelain | wc -l
git -c core.quotepath=false status --porcelain | cut -c1-2 | sort | uniq -c
```

기대: **103줄** = ` M` 44 · ` D` 22 · `??` 37.

**여기서 `uncommitted-restore.patch` 를 적용하지 않는다.** tar 작업 트리가 이미 최종 상태라 patch 가 겹친다. patch 는 B 경로용이다. ` M` 44 중 7건은 실제 변경이 아니라 LFS 필터 착시다(7단계).

## 5. `web/hero_viewer` — tar 작업 트리에서 빠진 21개

`.git` 에는 있으므로 HEAD 에서 꺼낸다.

```bash
git --work-tree="$OUT" checkout HEAD -- web/hero_viewer
find web/hero_viewer -type f | wc -l
find web/hero_viewer -type f -exec stat -f %z {} + | awk '{s+=$1} END {print s}'
git -c core.quotepath=false status --porcelain | cut -c1-2 | sort | uniq -c
find "$OUT" -type f -not -path "$OUT/.git/*" | wc -l
```

기대: **21개 · 28,978,232B** · ` M` 44 · ` D` 1 · `??` 37 · 프로젝트 **1,637** 파일

## 6. `teacher_data` — tar 에만 있는 67MB

```bash
shasum -a 256 design-docs/_tools/teacher_data/teacher_v1_10k.jsonl
```

기대: `47ea28969c2cf5f382068a823dc9ff38fc6f8bc1db84b6a8d2769096ac39a6ce`

tar 가 깨졌을 때만 재생성한다. 같은 해시가 나오면 원본과 바이트 동일이다.

```bash
python3 design-docs/_tools/sim_combat_teacher.py --runs 76 \
  --out /tmp/teacher_check.jsonl
shasum -a 256 /tmp/teacher_check.jsonl
```

기대: `133종 × 76런 = 10108 궤적` · 7~9초 · 해시 위와 동일.

## 7. (선택) LFS 착시 정리

`unity/.gitattributes` 가 `*.png`·`*.ttf` 를 LFS 로 잡는데 7개는 원본 바이너리로 커밋돼 있어, 손대지 않으면 늘 수정으로 보인다.

```bash
git update-index --assume-unchanged \
  unity/Assets/Icon.png \
  unity/Assets/Resources/Art/Logo.png \
  unity/Assets/Resources/Art/Skin/Sheet1_Frames.png \
  unity/Assets/Resources/Art/Skin/Sheet2_BarsIcons.png \
  unity/Assets/Resources/Art/Skin/Sheet3_TitleIcons.png \
  unity/Assets/Resources/Fonts/NanumGothic.ttf \
  "unity/Assets/TextMesh Pro/Fonts/LiberationSans.ttf"
git -c core.quotepath=false status --porcelain | cut -c1-2 | sort | uniq -c
```

기대: ` M` **37** · ` D` **1** · `??` **37** (75줄). 이 7개를 나중에 진짜로 바꿔도 git 이 못 보므로 읽기용 트리에서만 쓴다.

## B. HEAD 이력만으로 트리 세우기

`git archive` 는 LFS 필터를 태우지 않아 7개 착시가 없다. `web/hero_viewer` 도 HEAD 에 있어 **따로 꺼낼 필요가 없다**. 대신 tar 의 미추적 37개와 `gitignore` 78개는 이 경로로 재현되지 않는다.

```bash
B=/tmp/fons-head
mkdir -p "$B"
git -C "$OUT" archive HEAD | tar -x -C "$B"
cd "$B" && git apply "$A"/uncommitted-restore.patch
find "$B" -type f | wc -l
```

기대: `git apply` 무출력 · exit 0 · **1,522** 파일 (1,523 − 삭제 1). 이 1,522개는 A 트리와 **전수 바이트 동일**이다(2026-10-24 확인).

## 9. tar 를 잃었을 때 — `.git` 객체와 patch 만 남은 경우

`sha256 -c` 가 실패해 tar 를 버려야 하거나, tar 가 지워지고 `.git` 만 남았을 때의 길이다. **이력이 성한 한 추적 파일은 하나도 잃지 않는다.**

```bash
S=/tmp/fons-tar-loss
mkdir -p "$S"
tar -xzf "$A"/soul-commander-2026-10-24.tar.gz -C "$S" --include='./.git/*'
cp "$A"/uncommitted-restore.patch "$S"/
cd "$S"
git rev-parse HEAD
git reset --hard HEAD
git apply uncommitted-restore.patch
find . -type f -not -path './.git/*' | wc -l
```

기대:
- `669f0be936cec1e4ac3fc84f3af6a0fa7f60fe9f` — 이력은 `.git` 안에 있다(커밋 252 · `fsck` 0줄)
- `reset --hard` 1.0초 · 추적 **1,523**개 복원
- `git apply` 무출력 · exit 0 — patch 는 LFS 필터와 무관하다
- 파일 **1,522**개 (patch 가 지우는 1개 제외)

`web/hero_viewer` 21개(28,978,232B)는 HEAD 에 있으므로 따로 꺼낼 필요가 없다. 그 뒤 A 트리와 맞대면 **공통 1,522개 · 내용 불일치 0** 이다. 즉 tar 트리와 같은 내용이 된다.

**잃는 것 115개 (bundle 이 없을 때)** — tar 에만 있던 것들이다. patch 는 추적 파일의 차이만 담으므로 되살릴 수 없다.

| 갈래 | 수 | 되찾는 법 |
|---|---|---|
| `__pycache__/*.pyc` | 74 | 버려도 된다. 다음 실행에 다시 생긴다 |
| 미추적 작업 파일 | **37** (자체 실측) | 10단계 bundle. bundle 이 없으면 없다. `design-docs/_tools/check_*.py` 20개 · `policy_*.py` 5개 · `snapshots.js/json` · `editmode_map.json` · `TeacherGateTelemetry.cs`(+meta) 등 |
| gitignore 대상 기타 | 3 | 없다. 재생성하거나 포기한다 |
| `teacher_data` 67MB | 1 | 6단계 `--runs 76` 재생성 |

이 37개가 tar 를 지켜야 했던 이유다 — 이력이 아니라 작업 트리에만 있었다. 2026-10-25 에 37개만 담은 독립 bundle 로 옮겼다(10단계). 그 뒤로 tar 없이 잃는 파일은 78개다. 방안과 선택 근거는 [아카이브_미추적_보관_방안.md](아카이브_미추적_보관_방안.md) 에 있다.

**주의**: `reset --hard` 는 미커밋 삭제도 되살린다. 다만 아래 patch 가 그 삭제를 다시 적용한다. 결과적으로 두 트리의 `git status` 가 같다 — 삭제 1건(unity 쪽 `check_unity_health.sh`) · 수정 37건(자체 실측 · 2026-10-25). 그래서 이 경로는 A 트리와 파일 내용뿐 아니라 상태까지 같아진다.

## 10. 미추적 37개 — `untracked-2026-10-25.bundle`

tar 와 별개로 37개만 담은 git bundle. 부모 커밋이 없어 `.git` 도 tar 도 없이 clone 된다. 해시는 `sha256.txt` 에 함께 있다.

```bash
T=/tmp/fons-u37
git clone "$A"/untracked-2026-10-25.bundle "$T"
find "$T" -type f -not -path '*/.git/*' | wc -l
git -C "$T" rev-parse --short HEAD
```

기대: **37**개 · `b49939c` · 브랜치 `main` · 합계 779,235B · tar 안의 같은 37개와 바이트 불일치 0 (자체 실측 · 2026-10-25).

## 실행 기록 (2026-10-24)

이 문서의 명령을 그대로 돌려 위 수치를 확인했다. `tar` 풀기 1.17초 · `git fsck --full` 1.17초 · `teacher_data` 재생성 7.2~9.1초. B 트리 1,522개를 A 트리와 파일 단위로 맞대어 불일치 0을 확인했다.

같은 검사를 `tools/verify_archive.py` 로 묶은 뒤 다시 돌렸다 — **29개 항목 전부 통과 · 19.5초 · exit 0**(자체 실측 · 2026-10-24). 아카이브가 없는 환경에서는 `exit 2` 로 끝나는 것도 확인했다.

9단계(tar 손실)를 도구에 넣고 다시 돌렸다 — **38개 항목 전부 통과 · 22.5초(첫 실행) · 17.1초(재실행) · exit 0**, `--skip-regen` 은 36개 · 15.1초(자체 실측 · 2026-10-25). 같은 날 손으로도 돌려 `.git` 93MB 만으로 1,522개가 바이트 동일하게 복원되는 것을 확인했다.

10단계 bundle 을 만들어 tar 와 `.git` 없이 clone 했다 — **37개 · 779,235B · 불일치 0 · clone 0.07초**(자체 실측 · 2026-10-25). `shasum -a 256 -c sha256.txt` 가 tar 와 bundle 두 줄 모두 OK 였다.
